# Security boundaries and operator responsibilities

This project installs the official OpenAI Secure MCP Tunnel client and upstream
Desktop Commander MCP as a native systemd service. It is **not a sandbox**.

## Execution identity and authority

- The administrator explicitly selects an existing, non-root `dcmcp_user` in
  untracked inventory. The role never creates users, edits sudoers or chooses
  an account from the SSH login automatically.
- MCP tools operate with that account's ordinary filesystem and process
  permissions. If the account can `sudo`, the host's existing sudo policy still
  applies. A password prompt may be impossible to satisfy in an unattended
  MCP operation; the role never grants NOPASSWD automatically.
- By default, Desktop Commander's `blockedCommands` and `allowedDirectories`
  are left empty. **Do not interpret this as a policy boundary.** Configure
  upstream restrictions and/or a dedicated less-privileged Linux account if
  narrower access is required. Review the implications before assigning an
  administrative account to a tunnel.
- The runtime's process `HOME` is private and separate from the interactive
  account's home, but the default working directory is the user's existing
  home. A separate `HOME` does not isolate permissions or prevent access to
  files the Linux identity can ordinarily read.

## Control plane and secrets

- The tunnel establishes outbound HTTPS; the sample health endpoint listens
  on loopback only. Do not forward 8787 or expose the local admin UI to the
  public network. No inbound MCP firewall opening is needed.
- Provision a separate tunnel ID for each live MCP daemon. Do not use the same
  tunnel ID on two hosts, or start a second manual daemon against the service.
  The local instance lock does not coordinate remote hosts.
- Protect the runtime API key in the standalone `runtime.key` file, owned by
  `dcmcp_user`, mode `0600`, with private parent directories (`0700`).
  `tunnel.yaml` references it with a `file:` URI. Never put API keys in Git,
  `inventory/hosts.yml`, a command argument, a support log or a chat message.
- Give the runtime API key only the permissions needed to use the provisioned
  tunnel. The OpenAI account/workspace governs connector access. Review plugin
  permissions and who may invoke its tools. Revoke unused tokens and tunnels.
- `scripts/doctor.py` reports metadata and readiness only. It deliberately
  avoids printing config contents, tunnel IDs and tokens; it cannot guarantee
  OpenAI-side authorization or discover all possible misuse.

## Upgrades, operations and incident response

- Installation only stages a pinned, checksummed release. Offline preflight
  runs before activation. No active configuration file is generated by Ansible.
- Optional passive systemd monitoring reports local failures to journald;
  it does not restart the MCP daemon or provide remote alert delivery.
- A restart of the systemd service terminates in-flight MCP child commands.
  Avoid automatic restarts during long operations; check readiness and tool
  reachability from ChatGPT after a maintenance window.
- Always run a live upgrade from an independent SSH/console session, or use
  the separately detached controller. The detached controller explicitly
  accepts only local inventories; after interactive `sudo -v` authentication,
  it launches a root-owned systemd unit without storing sudo credentials.
  Do not run multiple Ansible controllers against the same host concurrently.
- On activation failure, the role can restore the old release selector but
  does not falsely claim that the old service is healthy. Preserve separate
  console access for recovery. Review journal messages without publishing
  credentials or private command output.
- For a suspected compromise, disable/revoke the ChatGPT plugin/tunnel and
  runtime key, investigate the affected Linux account, and review its access
  and process history. Rotating the key alone does not undo executed commands.

## Scope and validation

The current supported backend is the OpenAI Secure MCP Tunnel, not arbitrary
remote agents. Installation and ChatGPT tool execution were verified on an
RHEL 10.2 x86_64 host with SELinux Enforcing and on Ubuntu 26.04, but this is
not certification of all distributions, architectures, sudo configurations,
or upstream MCP tools. SELinux enforcing is retained where present; the role
never runs `setenforce 0` or adds broad SELinux policy exemptions.
